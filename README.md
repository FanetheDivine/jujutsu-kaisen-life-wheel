# 咒术回战 · 抽选人生转盘

转动数十轮因果轮盘，抽出一个属于《咒术回战》世界观的“人生”。

项目使用 **React 19 + 严格 TypeScript + Tailwind CSS v4 + Zustand** 构建界面与状态层，由 **Vite + vite-plugin-pwa** 打包为可直接部署到静态托管服务的可安装 PWA；运行时不依赖后端。

**当前版本：`v7.0`**（2026-11-12 · 规则对齐视频：四条结局线与彩蛋盘）

**在线直接玩**：<https://solar-cv.github.io/jujutsu-kaisen-life-wheel/>

旧地址 <https://solar-cv.github.io/jujutsu-kaisen-life-wheel/jujutsu-life-wheel.html> 会自动跳转到新版首页。

## 核心机制

### 前轮实时改写后轮

不是装饰性的选项列表，而是真正修改后续抽选权重：

- **加权**：抽到「死灭回游时期」，受肉体权重上升；抽到「涩谷事变」，一般市民（被卷入者）权重上升。
- **归零**：一般人类无法获得术式，凡人无法获得领域，「天与咒缚」也会排除领域。
- **整轮消失**：没开出领域时，「领域形态」直接记为「此轮不存」，命运帖里以「——」呈现。
- 转轮上方实时显示「前轮因果干涉」清单及每项概率变化，选项右侧显示相对基础几率的变化。

### 扇区面积等于当前几率

转盘按当前概率累加切割，而非等分。落点角度在目标扇区内随机偏置，再按旋转圈数与目标角度反算最终角度。极窄扇区会自动隐藏文字。

### 动态轮次队列

流程使用 Zustand 中可动态插入的 `stages` 队列。每轮落地后会按结果加入经历、缺席原因、技能、咒具、束缚、战斗回合、黑闪追击、御三家家门与战后成长等后续轮次。

### 命运回看与手转改命

每次实际抽取落地前，都会冻结当时的轮次队列、结果、战斗状态、选项概率与因果干涉，作为可在顶部序号回看的历史快照。

- **只读回看**：点顶部已完成且未跳过的序号，转盘与轮次面板切到该轮当时的选项与概率；当前人生不会被修改，点「返回当前」或转盘中央的「回」即可无损退出。
- **随时手转**：无需先回看，转盘圆环随时可以拖动改本轮结果；停留结果时拖动会替换本轮记录，而不是追加一条。
- **结果改变才生效**：拖动时指针所指扇区实时高亮，松手吸附到扇区中心；落回原结果完全不作废，只有停到另一个扇区才会改写。
- **改写因果**：回看中改写历史轮次时，会先恢复到该轮抽取之前，再按新手选结果重新推进；该轮原结果与之后的记录、动态插轮、战斗日志、终局一并作废，历史快照同步截断。

## 一轮人生包含什么

一轮通常包含 **36–74 轮，平均约 48 轮**：

| 段落     | 内容                                                                         |
| -------- | ---------------------------------------------------------------------------- |
| 起点     | 入场时期、性别、年龄、出身与存在形态、御三家家门、咒力资质                   |
| 内面     | 生得术式及性质、生得领域及其形态、效果与名称                                 |
| 性能     | 咒力总量、咒力操控、体术、体质、外貌、智谋，独立按 E–EX 七档抽选             |
| 刻度     | 咒力等级、努力、性格、运气、特殊天赋、束缚与羁绊                             |
| 经历     | 百鬼夜行、少年院、涩谷事变、死灭回游、新宿决战与终战之后；缺席还会继续抽原因 |
| 技艺     | 技能数量与具体技能；抽到咒具锻造后继续抽咒具数量与具体咒具                   |
| 事件战   | 在场即可开战，敌人按立场、阵营与强度匹配；战后抽成长与失去                   |
| 决战     | 决战阵营、回合数、双方逐回合出招与结算；评级较高时自动增加回合               |
| 宿傩专项 | 首次击败宿傩后可能解放原身并进入二番战；狱门疆提供一次性封印机会             |
| 终局     | 战后成长、命运结局与后世评价                                                 |

黑闪命中后可追加攻击。可以跳过单场战斗演出，也可以开启「事件战只出结算」。若角色在事件战中战死，后续经历会强制缺席，不再参加最终决战，结局也会锁定为相应的早死分支。

## 抽完之后能做什么

1. **查看检定**：六维、综合战力与生还倾向。
2. **生成名称**：按本次结果确定性生成术式名、领域名与称号，同一结果始终同名。
3. **回看与改命**：点顶部序号回看任意已抽取轮次，拖动转盘改写结果并重开该轮之后的因果；结果不变时不会动到当前人生。

## 交互与无障碍

- 点击转盘中央的「呪」，或聚焦后按 Enter / 空格，即可转动。
- 落地后转盘停在结果上，高亮扇区与选项保留；中心变为「→」，点一次（或按 Enter / 空格）直接开始下一轮转动，最后一轮点「→」直接进入终局。
- 点顶部已抽取的序号进入只读回看；回看中中心变为「回」，也可点提示条的「返回当前」无损退出。
- 转盘圆环支持鼠标 / 触屏拖动：松手停在另一扇区才会改写并作废后续，落回原结果不产生任何变化；中心按钮的转动 / 下一轮 / 返回行为不变。
- 停留期间转动、跳过此轮、一键抽完余生与跳过战斗演出暂时禁用，只能点中心箭头直接开抽；「一键抽完余生」自动连抽不受影响，仍会连续转动。
- 支持跳过此轮、跳过战斗演出与重新开始；跳过此轮不播放旋转，结果同样停留等待查看。
- 重新开始会作废在途旋转、自动连抽、历史快照与回看状态。
- WebAudio 咔哒声默认关闭；明暗主题自动跟随系统 `prefers-color-scheme`，并支持 `prefers-reduced-motion`。

## 本地开发

### 环境要求

- Node.js `>=22.12.0`
- pnpm `10.32.1`（`packageManager` 已固定）

```sh
pnpm install
pnpm dev
```

打开 Vite 输出的本地地址。开发服务器仅用于本地开发。

### 常用命令

| 命令                | 用途                                                |
| ------------------- | --------------------------------------------------- |
| `pnpm dev`          | 启动 Vite 开发服务器                                |
| `pnpm build`        | 严格类型检查并生成 `dist/`                          |
| `pnpm verify:dist`  | 校验 Manifest、Service Worker、图标与旧地址跳转产物 |

现有测试只断言纯逻辑与生产产物，不依赖 React 组件或页面 DOM：覆盖确定性随机工具、概率与因果干涉、动态插轮、战斗结算、派生命名、历史快照 / 只读回看 / 手转改写、转盘角度映射，以及生产 PWA 产物的结构校验和异常负例。

## PWA 与离线

- 通过 HTTPS 或 localhost 打开后，浏览器可将其安装到桌面或主屏幕，以独立窗口运行。
- 首次成功联网打开后，Service Worker 会预缓存构建后的 HTML、JavaScript、CSS、Manifest、图标与兼容跳转页，此后可离线打开应用外壳并抽选人生。
- 使用自动更新策略；新版本 Service Worker 安装后会接替旧版本。
- 直接双击源码 HTML 不会获得 Service Worker；请使用 `pnpm preview` 或 HTTPS 部署验证 PWA。

## 构建与 GitHub Pages

```sh
pnpm build
pnpm verify:dist
pnpm preview
```

生产文件输出到 `dist/`。Vite 使用 `base: './'`，因此可部署在 GitHub Pages 的项目子目录，不必把资源路径写死到域名根目录。`pnpm verify:dist` 会检查相对部署字段、Service Worker、预缓存、普通与 maskable 图标，以及旧地址跳转。

`.github/workflows/ci.yml` 会在 PR、`main` 分支推送和手动触发时执行完整 `pnpm check`。`.github/workflows/deploy.yml` 只在推送 `v*` 标签（例如 `v6.0.1`）或手动触发时执行完整检查并发布同一份 `dist/`；`main` 分支推送不再自动部署。首次使用时，在仓库 **Settings → Pages** 中将 Source 设为 **GitHub Actions**。

旧 `jujutsu-life-wheel.html` 的源码位于 `public/jujutsu-life-wheel.html`，只负责跳转，不再包含业务代码。

## 规则来源（视频对齐）

规则层正在按 UP 主**毓彧庾**的《咒术转盘》系列（B 站 `space.bilibili.com/198375523`，正传合集 87 集）逐期对齐。轮次名、扇面文案与条件插盘都来自对最近 10 集的逐帧还原：720P 下载、每 4 秒抽帧、OCR 画面文字，再按「轮次标题 / 本轮结果 / 扇面选项」三段切分归并。

- **权重口径**：视频画面从不显示百分比，因此权重按 `1 + 该扇面在 10 局录像里被抽中的次数` 估算。样本极小（多数轮次 0–4 次），只作参考，不是原作者配置；想改成等权只需把 `src/game/video/data.ts` 里的次数改成 0。
- **扇面口径**：选项清单是 10 局里出现过的可见并集，OCR 误识已人工校订，个别不确定的扇面被丢弃。
- **已对齐（P1）**：出身盘（身份、地点、时间点、性别、年龄、颜值、道德 + 咒灵 / 高层 / 诅咒师 / 魂穿专属支线）、天赋盘（生得术式、咒力总量、体质、效率、操纵、体术、天赋、特殊天赋、极之番、领域、无术式高级技巧）、临时终局两轮。
- **已对齐（P2）**：装备盘（咒具数量、类型、效果）、束缚盘（是否立下过 → 代价 → 收益）、评级盘（不入评级 / 四级→特级 / 特别一级）。
- **已对齐（P3）**：剧本线 82 轮，按八个篇章串起来——四百年前、怀玉、日常、百鬼夜行、剧情开始、幼鱼与逆罚、交流会、涩谷事变。每篇有参与盘（是否参加），答「否」只保留替补盘；`穿越后的时间点`晚于某篇时该篇整段跳过；家族、咒灵、无术式等身份条件按身份盘判断。
- **已对齐（P4）**：死灭回游 18 轮（是否参加 → 结界内地点、守卫天元、东京对手、宿夺舍、通缉虎杖等）、新宿决战 26 轮（是否参加 → 阵营、策略、赶到战场的时间、五宿对决胜负、诛伏赐死辩论盘等），以及战斗结算三连盘（胜负 → 伤势 → 成长，高/低天赋各一套成长盘，只看天赋不看时间点）。
- **已对齐（P5）**：战斗卡面流程——出招数 → 抽招式（每张卡面写「胜率+XX」）→ 博弈（强弱颠倒 / 不义游戏）→ 领域对抗 → 战斗盘·对手 → 胜负。胜负盘的权重不再固定：`50 + 招式胜率之和 × 0.6 + 博弈 + 领域`，夹在 10–90 之间，界面上的因果说明会写出「抽到几张、胜率多少」。底层仍是本仓库的加权随机内核，不是真的回合制战斗。
- **已对齐（P6）**：终局 16 轮——先转「是否活到 68 年后」；答「是」走 68 年后线（在哪里·68年后 → 人类是否存在 → 声望 → 是否参加战斗），答「否」走主角死后线（五宿对决胜利者 → 索与夏油由谁对付）与逆转时间线（回来的方式 → 回到的时间点 → 是否继续回溯 → 能否回到 68 年后 → 回不去了·决定）；最后是三条彩蛋盘（我掌握了咒力的核心! / 宿把手机砍坏了怎么办 / 打架前先恰个饭）与「观众看完会不会投币」。终局盘不受穿越时间点影响，什么时间线都要收尾。
- **待对齐**：无。P1–P6 已把录像里的 262 个轮次全部落进规则层，剩下的差异都是语料精度问题（见各期「粗糙处」）。
- **P2 的粗糙处**：咒具数量那一轮转的是纯数字扇面，OCR 只能确认 2 与 3，1 按同款补全；咒具效果与束缚代价各自只录到 1–2 帧，清单是可见扇面并集，个别断行碎片已丢弃。
- **P3 的粗糙处**：篇章归属与触发条件是从 10 局录像反推的——同一轮只在部分集出现，就只能按「时间点 + 参与盘 + 身份」推断，个别条件（如某轮是否只对咒术高层开放）证据不足；11 个只录到 0–1 个扇面的轮次按语义补到两个选项，否则玩家无从选择。
- **P4 的粗糙处**：死灭回游与新宿决战里大量细节盘只在一两局里露过一次，条件（阵营、咒灵侧、低道德侧）靠单局表现推断；「战斗盘·胜负」等结算盘的扇面在录屏里常被别的盘挡住，权重与文案按语义补足，胜率仍由 P5 的战斗流程决定。
- **P5 的粗糙处**：招式卡是录像战斗盘扇面的可见抽样（约 8 张），胜率数值照抄卡面但张数与组合远少于原作；博弈盘只做了「强弱颠倒 / 不义游戏 / 按部就班」三档修正，没有实现原作里换位与抢牌的完整规则；对手盘只列出录像里出现过的五位。
- **P6 的粗糙处**：终局文案同样来自 10 集录像的可见扇面，68 年后线只在 ep78/ep79 出现过、声望盘直接沿用评级扇面；两条广告彩蛋在录像里所有扇面都是品牌名（去转转 / 妙界），第二个选项是补出来让它转得起来的，不代表原作配置。

- **数据管线**：`scripts/video/prepare_source.py` 把 OCR 还原结果清洗成 `scripts/video/source.json`，再人工校订进 `src/game/video/data.ts`；剧本线与战斗结算盘由 `scripts/video/build_plot.py` 生成 `scripts/video/plot.json` 与 `src/game/video/plot.ts`（生成物勿手改，改条件改脚本里的 `ARCS` / `SETTLE` 表）；条件插盘表在 `src/game/video/flow.ts`。
